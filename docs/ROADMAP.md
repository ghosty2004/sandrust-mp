## Decisions made autonomously
- DIFF3-M4M7 (2026-11-06, F3, docs/phase3/diff-notes.md "M4–M7 steps"): judging rules added with the unoccupied/trailer/objects/chat/hit steps, each from original-vs-original evidence. (1) Tolerances are learned only from the step-directions the report judges (a bystander nudged 0.45 m by the actor's rolling car on the original would otherwise set the position tolerance of every step to 0.67 m). (2) `sender_vs_original` is not judged when the sender is the original itself (its own run-to-run variance, e.g. a short walk animation skipped on the way to a car door). (3) Scenario choices that avoid server races rather than judge them: the bystander of `veh_unoccupied_*` waits 60 m away (open.mp refuses a new 209 sender that is not the closest player to the server's stale car position — a 4.2 vs 4.5 m coin flip of where the peds stand), both trucks are created at once (open.mp streams new vehicles to a player only on that player's own syncs; an original client sitting in a car at rest sends none), the trailer window lasts until the rig is at rest. (4) `victim_health`: the original's shooter shows 56 for a victim at 53.8 (coarse health in S→C foot sync), judged against the original observer plus `sender_vs_original`. (5) samp-tracer's `bubbles`/`synced` read samp.dll build B data only (build A's player-pool layout differs; the diff lanes run build B).
- CURSOR-1 (2026-11-06, docs/phase3/m8a-notes.md "Mouse cursor"): samp's `user32!ShowCursor` stub (UR §5) is reproduced by redirecting gta_sa.exe's `ShowCursor` import (0x8582EC) instead of samp's 5-byte inline hook of the user32 export; GTA is the only other caller (d3d9/DXVK and d3dx do not import it), and the measured effect is the same (no `NtUserShowCursor` call from either client, same 32×32 cursor image in chat input / dialog / scoreboard). Our crash dialog calls the stub like samp's dialog does; our object editor keeps calling the real function like samp's (B 0x10073610 / 0x10073684). Left open (not exercised by this fix, no device-reset scenario measured): samp's lost-device handler re-arms the `WM_SETCURSOR` "SetCursor(NULL) once" flag (A 0x100c419b) and its reset handler calls `SetCursor(NULL)` and cursor mode 2 → 0 (UR §2.2); ours does none of the three.
- NET-R residuals (2026-11-06, docs/phase3/reconnect-notes.md): after the fix (process-global open-connection cookie, RakNet's strict request timer) ours matches the original's reconnect timeline in sockets, cookies and outcome for 15 s / 40 s / 6 s drops and a server cookie reseed. Left: (1) ours is ~15–25 ms quicker from "connection dead" / "attempt failed" to the next attempt's first request (lost 10.02–10.04 vs 10.04–10.06 s after the first unacked reliable send; silent attempt 6.03–6.04 vs 6.05–6.06 s), somewhere in packet → frame → RakClient::Connect's stop/start waits; (2) `0x19` → `0x0b` takes 11–12 ms in the original, 0–2 ms in ours (every join). Neither changes what the server sees beyond those milliseconds; both stay open as a measurement request (tracer hooks on RakPeer's Sleep loops A 0x10040700 / A 0x10042934 and the `0x19` path) rather than a guessed delay.
- JOIN-P residual: after the join dialog closes, our client's dialog response (62) and class request (128) can leave in one datagram; the original sent them in two datagrams 4.2 ms apart (2/2 captures). Order, content and reliability are identical and servers process messages, not datagram boundaries; RakNet packs whatever is queued in one update cycle.

They are listed in `tools/diff/rpc-decisions.tsv` (component `untriggerable`); `rpc_report.py` fails on any untriggerable id without such a row.
- DIFF2-D2 (2026-11-05, F1): the InitGame vehicle-model preload (B 0x100A1620; ours `vehlabels::preload`) probes every model with `0x0248 HAS_MODEL_LOADED` and releases with `0x0249` only the vehicle models GTA's streamer happens to hold at that moment; the probe sequence is compared in full, the set of released vehicle models (400–611) is accepted in `flow_join` / `gamemode_restart`.
