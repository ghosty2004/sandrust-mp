# NET-7 — C→S RPC send parameters and `rpcs::Outgoing`

## What exists (crates/samp-proto)

- `rpcs::OutgoingRpc: RpcPayload`, implemented by every C→S payload:
  `const RELIABILITY`, `const CHANNEL` (default `RPC_CHANNEL` = 0),
  `const PRIORITY` (default `RPC_PRIORITY` = 1), `const SEND_PARAMS`
  (`sync::policy::SendParams`, re-exported as `rpcs::SendParams`), and
  `to_message()`.
- `rpcs::OutgoingMessage { bits, reliability, channel, priority }`: a complete
  RPC body plus its send parameters. Send it with
  `conn.send_bits(&m.bits, m.reliability, m.channel)`.
- Per module (`player`, `session`, `ui`, `vehicle`, `world`; `remote` has no
  C→S RPC): `enum Outgoing`, `OUTGOING_IDS`, `decode_outgoing`,
  `outgoing_send_params`, `Outgoing::{id, write, send_params, to_rpc, to_message}`.
  These are generated by the `outgoing!` macro in `rpcs/mod.rs`, which also
  writes each type's `OutgoingRpc` impl, so ids, decoder and params come from one list.
- `rpcs::Outgoing` (wraps the module enums), `rpcs::decode_outgoing`,
  `rpcs::send_params(id)` (the RPC counterpart of `sync::policy::send_params`),
  `rpcs::outgoing_ids()`, `rpcs::OUTGOING_IDS_BY_MODULE`. `From` works from every
  payload type and every module enum.
- New typed payload `rpcs::session::PlayerConnect` (RPC 25). It produces the
  same bits as `session::build_player_connect`, which stays as it was.
- `Incoming::{id, write}` now exist in every module and at the top level
  (`InitGame::write` was added for 139).
- Tests are in `rpcs/outgoing.rs`. They check that every id in rpc-ids.md's send
  table, plus 27/181/182, appears exactly once, and that each id has the
  spec's params. They round-trip one sample per variant through RPC framing,
  and send the captured RPCs through `Connection::send_bits` to compare
  reliability, channel and bit length on the wire with the capture.

## Send parameters

Every C→S RPC send site the specs found passes **priority 1, channel 0**,
which rpc-ids.md and the preamble or send notes of player-state,
session-misc, ui-chat-audio, world-entities and vehicles all state. Every C→S
id has a stated reliability, so the specs leave no RPC's params unstated.
Two caveats apply to everything below:

- **Priority is never on the wire.** No capture can confirm it; it comes from
  static analysis only.
- **The channel is only on the wire for reliability 9/10** (ordered/sequenced).
  For reliability 8 the channel 0 cannot be observed.

## RPC 131: two reliabilities

The same payload is sent by two code paths. The GTA collision hook uses
RELIABLE_ORDERED, and that is `OutgoingRpc::SEND_PARAMS` and
`Outgoing::send_params()`. The type-14 pickup poll uses RELIABLE_SEQUENCED,
available as `world::OnPlayerPickUpPickup::POLL_SEND_PARAMS`. Use
`m.to_message().with_params(OnPlayerPickUpPickup::POLL_SEND_PARAMS)` for the
poll path. `rpcs::send_params(131)` returns the hook value.

Open point: rpc-ids.md lists 131's senders as "0x10013440, 0x10013520 | 10/9".
Read in order, that would give the hook rel 10 and the poll rel 9. But
world-entities.md §131 explicitly gives the hook (via 0x10013440) rel 9 and
the poll (0x10013520) rel 10. session-misc.md agrees for the poll function,
which also sends 97 at rel 10. The code follows world-entities.md. A capture
of both pickup kinds should settle it.
